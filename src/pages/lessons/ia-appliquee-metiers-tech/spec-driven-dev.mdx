Une spécification décrit le comportement attendu avant de choisir l’implémentation. Avec l’IA, elle sert de référence commune pour produire du code, préparer les tests et relire le résultat.

## Objectifs de la leçon

- Écrire une spécification centrée sur les comportements observables.
- Distinguer besoin, plan technique et critères d’acceptation.
- Vérifier un changement sans laisser le modèle définir seul sa réussite.

## Spécification, plan et tâches

La **spécification** répond à « que doit faire le système ? ». Le **plan** décrit comment le changement sera réalisé dans le projet. Les **tâches** découpent ce plan en travaux vérifiables.

L’ordre peut être itératif : une contrainte technique découverte pendant le plan peut exiger une clarification du besoin. En revanche, ne modifiez pas silencieusement les critères pour faire accepter une implémentation incorrecte.

Des outils comme GitHub Spec Kit structurent ce processus. Un fichier Markdown de projet peut aussi suffire. Une structure YAML inventée dans un cours n’est pas un standard officiel et ne garantit pas la compatibilité avec un outil.

## Cas concret : réinitialiser un mot de passe

L’exemple suivant concerne une application fictive, distincte du site de formation. Avant de coder, définissez les exigences de sécurité et les cas d’échec.

```markdown
# Réinitialisation du mot de passe

Besoin : permettre au titulaire d’un compte de retrouver son accès.
Entrée : une adresse email ; sortie publique uniforme, compte connu ou non.
Jeton : aléatoire, à durée limitée, à usage unique ; ne pas le journaliser.
Stockage : conserver un condensat du jeton, pas sa valeur exploitable.
Contrôles : limiter les demandes et vérifier la validité au moment de l’usage.
Tests : compte inconnu, expiration, réutilisation, jeton invalide et réussite.
Hors périmètre : changement du fournisseur d’email et refonte de l’authentification.
```

La réponse uniforme réduit le risque d’énumération, mais son texte seul ne suffit pas : les différences de temps ou de limitation peuvent aussi révéler l’existence d’un compte. Les seuils de limitation doivent être choisis pour votre service et mesurés, pas copiés comme des valeurs universelles.

Le test de développement utilise un fournisseur d’email simulé. N’écrivez pas le jeton dans les logs pour « faciliter le debug » et n’envoyez pas de message réel à une adresse cliente.

## Critères d’acceptation avant l’implémentation

Exprimez chaque critère sous forme de comportement :

- Un jeton expiré ne change pas le mot de passe.
- Un jeton déjà utilisé ne peut pas être réutilisé.
- Une requête pour un compte inconnu ne révèle pas son absence.
- Le secret n’apparaît pas dans les journaux.

Définissez ensuite les tests appropriés. Un test de l’expiration doit contrôler le temps ou utiliser une horloge injectable ; attendre une heure n’est pas nécessaire. Un test de réutilisation doit observer le refus du second usage, pas seulement la présence d’un champ en base.

## Passer au plan technique

Lisez le mécanisme d’authentification existant, la gestion des sessions et le service d’email. Le plan doit réutiliser les conventions et préciser les transactions ou contrôles nécessaires pour éviter les usages concurrents.

Après une réinitialisation, le traitement des sessions existantes doit être décidé dans la politique de sécurité. L’IA peut aider à identifier cette question ; elle ne doit pas inventer une réponse métier sans la signaler.

## Relire à partir de la spécification

Comparez le diff et les tests à chaque critère. Ajoutez les limites connues à la PR. Une spécification versionnée devient utile seulement si elle reste cohérente avec le comportement livré.

## À retenir

Les critères de réussite appartiennent au besoin. Le plan et le code doivent les satisfaire, avec des tests qui observent les comportements importants.
