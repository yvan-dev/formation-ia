Le projet final consiste à produire un `AGENTS.md` adapté à un dépôt et à vérifier son effet sur des tâches concrètes. La qualité se mesure dans l’usage, pas au nombre de règles ou d’agents créés.

## Objectifs de la leçon

- Améliorer les instructions à partir de défauts observés.
- Utiliser des exemples et des références cohérents avec le projet.
- Livrer un dossier de validation reproductible.

## Partir d’une version minimale exacte

Commencez par le contexte, les commandes, les contraintes importantes et le format de livraison. N’ajoutez pas toutes les règles imaginables. Lisez les instructions déjà présentes dans le dépôt et la documentation de l’outil choisi.

La longueur n’est pas un critère absolu. Supprimez les répétitions et les éléments faux ; conservez les informations qui permettent une bonne décision. Si un domaine devient trop détaillé, déplacez-le dans une référence clairement indiquée et vérifiez son chargement.

## Fournir des exemples utiles

Un exemple rend une attente plus concrète. Il doit correspondre aux conventions réelles : format de commit, rapport de validation ou composant existant. Ne présentez pas un style particulier comme une obligation industrielle universelle.

```markdown
## Rapport attendu — exemple de format

Changement : comportement modifié et raison.
Validation : commande, statut et nombre de tests si applicable.
Limites : contrôle non exécuté, dépendance ou hypothèse restante.
```

Une référence à un fichier maintenu est souvent préférable à une copie de code qui vieillira dans les instructions. Vérifiez que le fichier existe et que l’agent le lit pour la tâche concernée.

## Corriger le bon mécanisme

| Observation                               | Correction à examiner                                        |
| ----------------------------------------- | ------------------------------------------------------------ |
| L’agent modifie un fichier hors périmètre | Clarifier la mission et restreindre les écritures effectives |
| Une commande inexistante est proposée     | Corriger les références et relire le manifeste               |
| Une affirmation est inventée              | Exiger une preuve et vérifier les sources/outils disponibles |
| Une règle n’est pas suivie                | Examiner chargement, conflit, compréhension et contrôles     |
| Le résultat est inutilement complexe      | Préciser le comportement attendu et la réutilisation du code |

Ajouter « ne jamais inventer » ne garantit pas la vérité. Déplacer une règle en haut du fichier ne garantit pas son respect. Diagnostiquez la cause et observez l’effet de la correction.

## Construire un jeu d’évaluation

Utilisez au moins quatre familles de cas pour le projet final :

1. Une tâche normale dans le périmètre.
2. Une demande avec information manquante.
3. Une erreur d’environnement ou d’outil.
4. Une source contenant une consigne hostile.

Pour chaque cas, définissez résultat attendu, accès autorisés et contrôles. Conservez quelques cas de validation qui n’ont pas servi à ajuster les instructions. Répétez les cas sensibles lorsque la variabilité des sorties compte.

## Cas concret : correction de cours

Le fichier doit aider l’agent à préserver les slugs, corriger le texte et vérifier le rendu. Testez une correction de titre, un lien absent, une erreur de syntaxe MDX et un exemple qui contient une fausse consigne.

Vérifiez le diff et la navigation. Le contenu de l’exemple doit être traité comme du contenu pédagogique, sans changer la mission. Un build réussi ne prouve pas que les faits de la leçon sont exacts : la revue des sources reste distincte.

## Dossier final à remettre

Remettez le fichier d’instructions, les éventuels adaptateurs, les références utilisées et le tableau des cas. Pour chaque essai, indiquez outil, version/modèle, date, résultat, corrections et limites. Décrivez les permissions réellement configurées.

Passez les changements en PR avec une description compréhensible pour une personne extérieure à l’exercice. N’inventez pas des essais réussis. Une limite documentée est plus utile qu’une garantie impossible à démontrer.

## À retenir

Les instructions sont un artefact maintenu avec le code. Leur qualité repose sur l’exactitude, les contrôles effectifs et l’évaluation sur des cas nouveaux.
