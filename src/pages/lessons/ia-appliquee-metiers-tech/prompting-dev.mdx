Un prompt de développement utile relie un besoin à un dépôt réel : ses conventions, ses dépendances et ses tests. Il réduit les changements inutiles et fournit au relecteur les moyens d’évaluer le résultat.

## Objectifs de la leçon

- Préparer une demande adaptée à la taille du changement.
- Demander des preuves de comportement plutôt qu’une assurance verbale.
- Relire le résultat et les limites de l’exécution.

## Commencer par le dépôt

Avant de modifier, identifiez les fichiers concernés, les scripts du projet et les contraintes existantes. Demandez au système de citer les fichiers lus lorsqu’ils fondent une décision. Un chemin proposé mais non vérifié ne constitue pas une preuve.

Pour une petite correction, une demande courte peut suffire. Pour un changement qui touche plusieurs couches, un plan aide à clarifier les étapes et les inconnues. Le formalisme doit rester proportionné au risque.

## Un prompt de modification réutilisable

```text
Besoin : le formulaire doit annoncer les erreurs au lecteur d’écran.
Contexte : lire le composant, les styles et le test du formulaire.
Contraintes : conserver les routes, la validation et les composants existants.
Implémentation : proposer le plus petit changement couvrant le besoin.
Vérification : tester une soumission invalide au clavier et un cas valide.
Livraison : décrire le comportement, les fichiers modifiés et les contrôles exécutés.
Signaler les limites et les changements hors périmètre nécessaires.
```

La demande explique ce que l’utilisateur doit pouvoir faire. Elle n’impose pas une bibliothèque supplémentaire sans raison.

## Décrire les comportements, y compris les erreurs

Un ticket « ajouter un export » peut cacher des exigences d’autorisation, de format, de volume et de confidentialité. Précisez les cas attendus avant la génération du code : qui peut exporter, quelles données, quel état vide, quelle erreur et quelle taille maximale ?

Pour une API fictive, un format d’erreur peut suivre **RFC 9457, Problem Details for HTTP APIs**, qui remplace RFC 7807. Le choix exact des codes HTTP doit rester cohérent avec le contrat du projet. N’appliquez pas automatiquement un code universel à toutes les erreurs de validation.

```json
{
  "type": "https://example.com/problems/invalid-limit",
  "title": "Paramètre de pagination invalide",
  "status": 400,
  "detail": "La limite doit être un entier positif dans la plage autorisée."
}
```

Cet exemple est un contrat pédagogique, pas une API déjà présente dans le site de formation. Un message d’erreur ne doit pas révéler de secret ni de détail interne sensible.

## Demander une justification vérifiable

Demandez les hypothèses, les options pertinentes et les raisons d’un choix. Une justification utile s’appuie sur une contrainte du projet ou une observation mesurée. Il n’est pas nécessaire de demander la chaîne de pensée interne du modèle.

Pour un refactoring, exigez que le comportement public reste identique et que les tests pertinents soient comparés avant/après. Ne confondez pas des tests modifiés pour passer avec une preuve de non-régression.

## Relire la livraison

Vérifiez le diff, les fichiers ajoutés, les dépendances, les effets sur les données et les commandes exécutées. Une commande terminée avec succès peut avoir exécuté zéro test : regardez le compte et le résultat du runner. Un test non lancé doit rester marqué comme non exécuté.

La revue doit couvrir les aspects que les outils ne jugent pas : adéquation au besoin, lisibilité et complexité. Si une commande échoue, faites distinguer problème d’environnement et défaut du changement avant de décider de la suite.

## À retenir

Le prompt de développement sert de contrat de travail vérifiable. Le diff et les contrôles donnent la preuve de livraison.
