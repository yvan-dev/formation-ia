Quand une sortie IA intervient dans une authentification, une autorisation ou une opération sur des données, une erreur plausible peut devenir un incident. Les contrôles doivent cibler le comportement dangereux, pas seulement la compilation.

## Objectifs de la leçon

- Détecter des erreurs de sécurité dans un code généré.
- Vérifier les dépendances avant installation.
- Choisir des tests négatifs qui prouvent un refus attendu.

## Des erreurs qui passent le cas nominal

Un endpoint peut retourner la bonne réponse et oublier le contrôle du propriétaire. Un jeton valide peut être décodé alors que les jetons falsifiés ne sont jamais rejetés. Le fonctionnement du cas nominal ne prouve donc pas la sécurité.

Les mêmes règles s’appliquent au code humain et au code assisté. Ne supposez ni que le modèle ignore toute notion de sécurité, ni qu’une consigne « code sécurisé » suffit à valider sa sortie.

## Exemple 1 : requête SQL

Exemple Python/SQLite pédagogique. La concaténation d’une entrée dans une requête est dangereuse :

```python
# À ne pas utiliser : entrée intégrée au texte SQL
query = f"SELECT id FROM users WHERE name = '{username}'"
```

Une requête paramétrée transmet la valeur séparément :

```python
# SQLite : le placeholder dépend du pilote utilisé
rows = connection.execute(
    "SELECT id FROM users WHERE name = ?",
    (username,),
).fetchall()
```

Les paramètres protègent les valeurs, pas un nom de table construit dynamiquement. Pour des identifiants SQL variables, utilisez une liste autorisée et les primitives du pilote. Le contrôle d’autorisation reste une étape distincte.

## Exemple 2 : jeton d’authentification

Décoder un JWT permet de lire son contenu ; cela ne prouve pas sa signature. Utilisez une bibliothèque maintenue et sa fonction de vérification, avec algorithmes attendus, expiration, émetteur et audience selon le contrat.

Ne copiez pas un simple `verify(token, secret)` comme solution universelle. Les clés, algorithmes et règles de validation dépendent du système. Après l’authentification, contrôlez aussi le droit d’accéder à la ressource ciblée.

## Exemple 3 : contenu HTML

En React, une interpolation de texte est échappée. Une insertion via `dangerouslySetInnerHTML` demande un traitement spécifique si le contenu n’est pas fiable. Si vous n’avez besoin que d’un nom, rendez du texte :

```jsx
function Greeting({ name }) {
  return <p>Bonjour {name}</p>;
}
```

Si du HTML est nécessaire, choisissez une stratégie de sanitisation adaptée et documentée. Une regex supprimant quelques balises ne constitue pas un parseur HTML sûr.

## Dépendances et slopsquatting

Avant une nouvelle installation, vérifiez le registre officiel, le dépôt, l’éditeur, la licence, les versions et les alertes. Un nombre élevé de téléchargements ou un nom existant ne garantit pas l’innocuité.

Le **slopsquatting** exploite des noms de packages inventés par des modèles. Le **typosquatting** exploite la confusion avec un nom connu. Le lockfile améliore la reproductibilité et les contrôles d’intégrité, mais ne rend pas sûre une dépendance malveillante choisie au départ.

## Tester des refus et des invariants

| Cas                                    | Preuve attendue                                |
| -------------------------------------- | ---------------------------------------------- |
| Jeton falsifié ou expiré               | Requête refusée, aucune opération protégée     |
| Accès à la ressource d’un autre compte | Aucun contenu ni mutation autorisés            |
| Entrée ressemblant à du SQL            | Valeur traitée comme donnée, résultat conforme |
| Échec du service de validation         | Pas de passage silencieux en accès libre       |

Une table qui existe encore après un test SQL ne suffit pas à prouver l’absence d’injection : le résultat peut avoir été élargi sans supprimer la table. Vérifiez la réponse exacte et l’invariant métier.

## À retenir

La revue critique cherche les erreurs que le cas nominal laisse passer. Vérifiez les refus, les effets et la provenance des dépendances.
