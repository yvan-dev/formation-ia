Planifier avant un changement complexe permet de repérer les inconnues et les dépendances à un moment où les corriger coûte encore peu. Le principe « plan-first » doit aider le travail, pas imposer un document volumineux à chaque correction.

## Objectifs de la leçon

- Choisir le niveau de planification adapté au changement.
- Écrire un plan fondé sur les fichiers et contraintes réels.
- Réviser le plan lorsqu’une nouvelle preuve apparaît.

## Quand un plan apporte de la valeur

Un changement de texte peut se résumer à un fichier et une vérification visuelle. Une migration, une modification d’authentification ou un changement traversant plusieurs composants justifie un plan plus explicite.

Le plan est utile quand il rend visibles le périmètre, les étapes, les critères de réussite et les risques. Il ne garantit pas que l’implémentation sera correcte, et il ne remplace pas la revue du résultat.

| Changement                       | Plan raisonnable                                         |
| -------------------------------- | -------------------------------------------------------- |
| Faute dans une légende           | Fichier concerné et contrôle de rendu                    |
| Nouveau comportement d’interface | Composants, états, tests et accessibilité                |
| Migration de données             | Préparation, exécution testée, contrôles et restauration |

## Lire avant de planifier

Un agent peut proposer des chemins plausibles qui n’existent pas. Faites lire la structure réelle, les composants analogues et les scripts disponibles. Un plan doit préciser ce qui est observé et ce qui reste une hypothèse.

Pour une fonctionnalité, décrivez d’abord les critères de réussite. Les tests et le plan doivent découler du comportement attendu ; ils ne doivent pas être inventés après avoir vu le code généré.

## Un plan en cinq parties

```markdown
# Changement : état vide de recherche

Besoin : distinguer zéro résultat d’une erreur de chargement.
Périmètre : composant de recherche et ses styles ; route inchangée.
Étapes : lire le contrat, ajouter l’état vide, relier les messages accessibles.
Vérification : zéro résultat, erreur simulée, cas nominal et clavier.
Inconnue : le moteur expose-t-il déjà un état d’erreur ? À vérifier avant modification.
```

Pour une action sur des données, ajoutez l’impact, les préconditions et le moyen de retour arrière. Pour un déploiement, précisez le point de décision et les observations après mise en ligne.

## Valider les décisions utiles

La revue du plan cherche les erreurs de besoin, les changements superflus et les risques oubliés. Il n’est pas nécessaire de faire approuver chaque petit choix de nommage. Une autorisation déjà donnée pour préparer une PR ne doit pas être redemandée à chaque étape réversible.

Une question devient nécessaire lorsqu’une information manquante empêche de choisir correctement, ou lorsqu’une action dépasse le périmètre autorisé. Continuez les parties indépendantes pendant que cette décision est attendue.

## Adapter le plan à l’exécution

Si la lecture d’un fichier révèle un composant réutilisable, mettez le plan à jour plutôt que d’ajouter celui prévu initialement. Si un test montre une hypothèse fausse, corrigez le diagnostic avant de poursuivre.

Une boucle de correction doit être bornée par le temps, le coût ou des conditions d’arrêt pertinentes. « Toujours trois tentatives » n’est pas une règle universelle. Arrêtez une répétition qui n’apporte aucune information nouvelle et rapportez le blocage précis.

## Cas concret : ajout d’une notification

Un plan incomplet peut oublier l’autorisation, les doublons ou l’échec du fournisseur. Un plan utile prévoit l’événement déclencheur, l’idempotence, le contenu minimal et un environnement de test qui n’envoie pas de message réel. L’envoi en production constitue une action distincte de la préparation du code.

## À retenir

Un plan utile rend les décisions et les inconnues visibles. Il doit évoluer avec les preuves recueillies pendant le travail.
