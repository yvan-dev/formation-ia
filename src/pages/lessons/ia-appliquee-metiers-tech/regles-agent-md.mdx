`AGENTS.md`, au pluriel, est un format ouvert pour donner du contexte et des instructions aux agents de code. Son rôle est d’aider l’outil à travailler dans le dépôt ; il n’accorde pas de permissions et ne garantit pas l’exécution correcte des règles.

## Objectifs de la leçon

- Nommer et positionner le fichier adapté à l’outil.
- Écrire des instructions pertinentes et vérifiables.
- Séparer conventions de projet et restrictions effectives.

## AGENTS.md, CLAUDE.md et autres formats

Le format ouvert s’appelle **AGENTS.md**. Un fichier `AGENT.md` au singulier peut être une convention interne, mais ne doit pas être présenté comme le nom standard ni supposé chargé automatiquement.

Claude Code utilise notamment `CLAUDE.md`, et GitHub Copilot propose ses fichiers d’instructions propres. Le support d’`AGENTS.md`, les fichiers imbriqués et leur portée dépendent de l’outil et de sa version. Consultez la documentation puis observez le chargement réel.

Le chemin des leçons de ce parcours conserve `agent-md` pour maintenir les URL existantes. Cela ne change pas le nom du fichier à créer dans le projet final : `AGENTS.md`.

## Partir des informations qui changent le travail

Décrivez le projet, les commandes utiles, les conventions importantes et la manière de vérifier le résultat. Ajoutez les contraintes que l’agent ne peut pas déduire correctement du code seul.

```markdown
# Instructions du projet

Ce site utilise Astro et MDX.
Conserver les routes existantes lors d’une correction de contenu.
Lire la collection de cours avant de modifier la navigation.
Après modification : exécuter le build et vérifier le rendu concerné.
Rapporter les contrôles exécutés et ceux restés indisponibles.
```

Ces instructions doivent correspondre au dépôt. Une règle courte mais fausse est plus nuisible qu’une explication un peu plus longue et exacte.

## Précision sans rigidité inutile

« Faire du bon code » ne précise pas les attentes. Préférez « réutiliser le composant de bouton existant » ou « tester le refus d’accès à la ressource d’un autre compte ».

Évitez les métriques arbitraires : toutes les fonctions sous vingt lignes, chaque fichier sous cinquante lignes ou une couverture totale sans lien avec les risques. Elles peuvent provoquer des abstractions inutiles et des tests peu informatifs.

Une courte raison peut aider : « garder les clés de stockage pour conserver la progression des utilisateurs ». Le contexte n’est pas toujours du bruit ; il évite parfois une mauvaise interprétation d’une règle.

## Les permissions vivent dans l’environnement

Une section « ne pas déployer » précise l’intention, mais ne retire pas un accès de déploiement. Configurez les outils, chemins, identifiants et destinations réseau dans l’environnement utilisé. Les instructions complètent ces contrôles.

Ne mettez pas de secret dans le fichier, même si vous pensez qu’il sera uniquement lu par un agent local. Il peut être versionné ou transmis à un service.

## Évaluer avec un nouvel arrivant et des cas réels

Faites relire le fichier à une personne qui ne connaît pas le projet. Vérifiez qu’elle peut trouver les commandes, le besoin et les critères de livraison. Ses questions révèlent des informations manquantes ; elles ne prouvent pas que l’agent échouera toujours, mais orientent la correction.

Testez aussi une tâche nominale, une dépendance manquante et une demande hors périmètre. Observez les fichiers modifiés, les commandes et les limites signalées.

## Versionner les changements

Les instructions évoluent avec le code. Passez leurs modifications en revue et supprimez les règles devenues fausses ou répétées. L’objectif est une source cohérente et accessible, pas un document qui grandit à chaque incident sans nettoyage.

## À retenir

Un bon fichier d’instructions est exact, cohérent et évalué dans l’outil réel. Il accompagne les contrôles d’accès sans les remplacer.
