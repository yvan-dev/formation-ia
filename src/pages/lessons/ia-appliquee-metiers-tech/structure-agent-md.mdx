Une structure d’instructions doit permettre de trouver rapidement le contexte, les commandes et les attentes de livraison. Le modèle suivant est une base adaptable, pas une norme qui garantit à elle seule la qualité de l’agent.

## Objectifs de la leçon

- Construire un fichier d’instructions lié au dépôt.
- Séparer règles permanentes et mission ponctuelle.
- Fournir un exemple de restitution honnête et utile.

## Contexte stable et tâche du moment

`AGENTS.md` contient surtout les informations durables : stack, commandes, conventions et règles de contribution. Le ticket ou le prompt porte le besoin du moment. Évitez d’inscrire une mission temporaire dans le fichier global si elle ne doit pas s’appliquer aux tâches futures.

L’ordre des sections doit favoriser la lecture et rendre les contraintes importantes visibles. Il n’existe pas d’ordre universel qui assure une « attention maximale » du modèle.

## Un modèle pour ce dépôt

Exemple à adapter et à vérifier avant adoption :

```markdown
# Formation IA — instructions de contribution

## Projet

Site statique Astro avec leçons MDX, composants React et recherche Pagefind.

## Repères

- Programme : src/content/courses/ia-appliquee-metiers-tech.json
- Leçons : src/pages/lessons/ia-appliquee-metiers-tech/
- Composants : src/components/
- Styles : src/styles/

## Préparation

Lire les fichiers concernés et les conventions applicables.
Préserver les routes et les clés de progression sauf demande explicite.

## Validation

- npm run build : génération des pages et de l’index de recherche
- npm run lint : règles de code
- npm run test:e2e : parcours navigateur pertinents
  Vérifier que les tests annoncés ont réellement été exécutés.

## Livraison

Décrire le problème, le comportement obtenu et les validations.
Signaler les contrôles indisponibles et les limites observées.
Ne pas déduire une autorisation de merge ou de publication de la création d’une PR.
```

Ce modèle ne crée pas de politique de permissions. Configurez séparément les accès dans l’outil et l’environnement. Si le dépôt possède déjà des instructions applicables, harmonisez-les au lieu d’ajouter une seconde source contradictoire.

## Adapter les commandes

Une commande doit fonctionner dans le bon répertoire et avec les prérequis nécessaires. Documentez ceux qui ne sont pas évidents : version de Node, navigateur E2E et variables requises, sans valeur secrète.

Ne copiez pas `npm test` si le projet ne définit pas ce script. Ne présentez pas un outil de validation absent comme déjà installé. Pour un générateur OpenAPI, par exemple, utilisez le validateur réellement retenu dans le projet.

## Montrer une restitution attendue

```text
Changement : le formulaire distingue liste vide et erreur réseau.
Vérification : build réussi ; scénario nominal et erreur simulée vérifiés.
Limite : le service distant réel n’a pas été interrogé.
Point restant : publication selon le processus du projet.
```

L’exemple ne doit pas annoncer des résultats fictifs comme des faits exécutés. Dans le fichier d’instructions, identifiez-le comme un format de sortie à remplir avec les observations réelles.

## Gérer un blocage

Demandez de distinguer information manquante, accès refusé, problème d’environnement et défaut du code. Le système peut poursuivre les travaux indépendants, mais ne doit pas inventer une preuve ni contourner une restriction pour terminer.

Un seuil de taille de diff peut servir d’indicateur de revue, pas de garantie. Une petite modification d’autorisation peut être critique ; une grande mise à jour documentaire peut rester simple. Basez l’escalade sur le risque et les capacités réelles de vérification.

## Rendre les références maintenables

Réutilisez les documents existants, comme le guide de design, plutôt que recopier les tokens partout. Vérifiez les chemins et demandez la lecture des références nécessaires : un lien n’est pas toujours chargé automatiquement.

## À retenir

La structure rend les informations trouvables. L’exactitude des commandes, la cohérence des règles et la qualité des preuves restent essentielles.
